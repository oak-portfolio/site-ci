## Agents Are Overhyped Until They Own The Work

I had been using agents for long enough to feel the gap between the demo and the daily reality.

Paid tools, other teams' agents, and agents I built myself could all do impressive one-off tasks. The weak point came after the task finished. I still had to read the logs, inspect the run, patch the prompt, notice the missing report, update the browser step, and decide what should happen tomorrow.

That made the word "agent" feel inflated. If I still carried the plan, the memory, the judgment, and the next decision, I was still the operator. The tool had improved the interface, but the work still lived in my head.

The industry has been circling the same problem. Anthropic writes about long-running harnesses because agents need state, budgets, continuation, and recovery. <BrandIconLink provider="codex" label="Codex /goal" href="https://github.com/openai/codex/releases/tag/rust-v0.128.0" /> exists because longer work needs a persistent objective. Ralph-style loops, Paperclip, Karpathy's <BrandIconLink provider="github" label="autoresearch" href="https://github.com/karpathy/autoresearch" />, and Arize's telemetry writing all point in the same direction: once the work lasts longer than one chat, the model becomes only one piece of the job.

The idea that really stuck with me came from <BrandIconLink provider="factory" label="Factory Missions" href="https://factory.ai/news/missions" />. Their framing was simple: stop trying to make one agent do everything. Use an orchestrator, workers, validators, and research agents because each role fails in a different way. That changed how I thought about my own systems. I stopped asking, "Can one agent handle this?" and started asking, "What team would make this work trustworthy?"

## The In-House Need Made It Serious

The need became concrete during a brief HyperSkalers project. One of the projects there was about building relationships through in-house agent teams instead of handing the work to another vendor workflow and hoping it adapted.

While working through that, the actual shape of the problem became clearer: find the right people, understand why they fit, keep the outreach relevant, follow the conversation, and avoid turning serious networking into noisy outbound.

The obvious tools had tradeoffs. Some were expensive. Some were locked into one platform. Some were slow to adapt when the platform changed. Some created restriction risk because the user had very little control over how the work was being done.

The conclusion was clear enough: an in-house agent team would be more interesting than another vendor workflow. It could stay close to the data, explain its own runs, improve from real outcomes, and keep sensitive choices behind approval.

That was the point where I started going deeper. The goal was bigger than <BrandIconLink provider="linkedin" label="LinkedIn automation" />: I wanted to know whether agent teams could run an actual business workflow without me holding every step together.

## LinkedIn Became The First Real Success

LinkedIn Growth Loop became the first project where the idea actually worked for me.

The visible workflow was relationship work. The deeper project was autonomy: agents choosing targets, preparing context, acting inside limits, reporting what happened, learning from outcomes, and feeding the next pass without me manually operating the whole thing.

Among the agent projects I had tried, this was my first real success with multiple agents doing the jobs at high autonomy. The autonomy was bounded: routine work moved out of my hands, while override, approval, and rollback stayed available.

<BrandIconLink provider="linkedin" label="LinkedIn" /> was useful because the feedback was immediate and hard to fake. Someone connects, ignores, replies, keeps talking, or makes it obvious the note missed. In professional and high-skill relationship work, that is risky. A bad interaction is public enough to care about. But it is also worth it because those real outcomes are what a self-improving system can actually learn from.

The discovery was almost accidental. Start with one small skill, run it against the real world, evaluate the result, then widen the loop only after the team can explain what happened. Without that feedback, agent work turns into weeks of polishing imaginary behavior.

## The First Daily Loop

The first version was intentionally small.

I had a list of people from CRM context and <BrandIconLink provider="linkedin" label="LinkedIn" /> Navigator-style targeting. The daily job was simple: review the list, understand why each person belonged there, write a personalized connection note, send or skip, then record what happened.

That small loop had the right shape. It had a target, context, an action, a result, and a next decision. It also had real constraints: avoid generic notes, avoid blasting people, stop repeating stale examples, and save model calls for decisions that needed judgment.

Later, the scope widened into target discovery, feed interaction, response tracking, follow-up state, and outcome comparison. Starting small made that expansion possible because the early runs created feedback quickly instead of hiding problems behind a large automation plan.

## Orchestrator, Workers, Validators

The first real design decision was to stop treating the workflow as one agent. I split it into two operating groups:

1. <KeywordBadge>People work</KeywordBadge> handled target lists, scoring, context, connection notes, send-or-skip decisions, and follow-up state.
2. <KeywordBadge>Public interaction</KeywordBadge> handled relevant posts, cooldown checks, duplicate-risk watching, and response signals.

Around those groups, I needed the same shape I liked from Factory's mission model: an orchestrator to keep the work moving, workers to own specific jobs, validators to stop unsafe actions, and research agents to keep the environment fresh.

A bad target, a weak note, a browser miss, and a duplicate-risk problem needed separate owners. Filing all of them under "the agent failed" would hide the fix.

Once the roles were separated, the reports got sharper. I could tell whether a miss belonged to targeting, writing, browser control, duplicate prevention, research, or orchestration instead of treating everything as a prompt problem.

## Harnesses Were Just The Tools

<BrandIconLink provider="openclaw" label="OpenClaw" /> was my main worker and orchestrator for this version. It ran the recurring work, coordinated tools, reported status, and kept the lanes moving.

<BrandIconLink provider="hermes" label="Hermes" /> was useful in a different role. The overall sentiment around it was that Hermes worked better for self-improvement and memory-oriented work, so I treated it more like an advisor: research what changed, learn from the feedback loop, keep audience and platform signals fresh, and feed better advice back into the next decision.

That pairing was personal preference. I could have forced everything into one harness, but I wanted to see what each one was actually good at, then make them cooperate instead of pretending one tool should own every job.

The broader lesson traveled beyond the specific tools. Today the same operating model could be built with <BrandIconLink provider="codex" label="Codex" />, <BrandIconLink provider="claudecode" label="Claude Code" />, <BrandIconLink provider="openai" label="OpenAI Agents" />, Ralph-style loops, Factory-style missions, or another open-source harness. The team design mattered most: execution, research, memory, reporting, review, validation, and approval each needed a clear job.

That separation made autonomy easier to trust. The research side could advise without silently changing live behavior. The orchestrator had to turn evidence into a proposal, a low-risk change, a skip, or an approval path.

## Telegram Became The Control Room

Modern agent harnesses are moving beyond the terminal because messaging channels already feel natural. <BrandIconLink provider="telegram" label="Telegram" />, <BrandIconLink provider="slack" label="Slack" />, <BrandIconLink provider="discord" label="Discord" />, <BrandIconLink provider="imessage" label="iMessage" />, and similar surfaces are where people already check status and respond quickly. That makes agent work feel less like babysitting a terminal and more like managing a teammate.

<BrandIconLink provider="openclaw" label="OpenClaw" /> and <BrandIconLink provider="hermes" label="Hermes" /> already supported messaging channels, including Telegram-style control. The built-in reporting worked, but each channel has different formatting strengths. Plain text was leaving too much value on the table, and over months it drained attention. A report would arrive, but I still had to parse the story: what changed, what failed, whether I needed to care, and where the useful detail lived.

So I built a dedicated <KeywordBadge>Telegram control room</KeywordBadge> and forced the harnesses to report through it. It supported the richer Telegram formats I actually wanted: sections, formatting, controls, compact summaries, and hidden detail. Every message had two versions inside it. The visible layer was human-friendly and ADHD-friendly: status, key metrics, failures, recommendation, and controls. Underneath, the same message carried machine-friendly detail: run IDs, run details, artifact paths, source references, proposed changes, logs, and control actions.

## Browser Control Kept The Cost Honest

APIs are more valuable than ever in the agent era. They are still the cleanest path when they expose the work clearly. I kept running into cases where the practical route still lived in the browser.

Some workflows live inside the same browser surfaces humans already use. API paths can be limited, expensive, messy, or too narrow for the actual job. In those cases, browser control becomes part of the agent stack.

That choice reduced API dependency and created a different kind of work. Browsers change. Platforms change. Labels move. DOM structure shifts. A browser agent has to handle small changes cheaply instead of spending a heavy model call on every tiny step.

I made routine actions as programmatic as possible: SOPs, recorder flows, page calibration, cached control knowledge, button and field checks, page-state checks, and bounded recovery before heavier intelligence. Known actions should run cheaply. Changed pages should try narrow recovery before asking a model to reason from scratch.

The model still belonged in the judgment-heavy moments: understanding a person's context, deciding whether a note sounded human, comparing interaction strategies, and summarizing the result. A <BrandIconLink provider="gemini" label="Gemini Flash-class model" /> was enough for those steps. I saved the heavier models for work that actually needed them.

After that, improvement became a chain instead of a feeling:

3. <BrandIconLink provider="hermes" label="Hermes" /> added research, memory context, and platform-risk signals.
4. <BrandIconLink provider="openclaw" label="OpenClaw" /> turned that evidence into a proposed improvement or a bounded change.
5. The next Telegram report explained what changed, what stayed blocked, and what the following run should use.

Inside this workflow, the same idea became practical when reports became the next run's working material.

## One Failure That Forced Better Rules

There were plenty of failures over months: stale selectors, noisy targets, weak examples, missing context, skipped reports, and decisions that looked reasonable until real feedback exposed the gap.

One visible failure came from the feed agent sometimes struggling to tell two posts apart. Different posts from the same person could look too similar unless the run proved exactly which post it was touching.

For relationship work, that mistake is visible. A duplicate public interaction makes the system look careless. It also exposed a rule I wanted everywhere: prove the object first, or stop.

<ExcalidrawFigure
  src="https://link.excalidraw.com/readonly/yclnfYDTW0bAkZ0gjv4P?darkMode=true"
  title="LinkedIn Growth Loop stop rule Excalidraw diagram"
  caption="The failure turned into a simple rule: prove the object first, or stop before public action."
/>

I moved that risk into rules and run memory. The agent needed fewer chances to be careful and more places where the run would refuse to continue.

After that change, a report could show more than completion. It could show that the risky behavior had a clear stop condition around it. The next version required reliable post identity before action instead of trusting the agent to notice the problem later.

For me, this was the first clear success at building agents that self-automate in a bounded lane without me operating every step.
